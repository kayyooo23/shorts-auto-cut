# Shorts Auto-Cut — Backend

FastAPI + Celery + SQLite(dev)/Postgres(prod). Загружаешь видео → в фоне
транскрибируется и режется на моменты → отдаёшь результат фронтенду для
редактирования субтитров/баннера и постановки в очередь на публикацию.

## Структура

```
backend/
  app/
    main.py         — FastAPI, все HTTP-эндпоинты
    models.py        — таблицы БД: Video, Moment, Subtitle
    schemas.py        — Pydantic-схемы для API
    tasks.py           — Celery-задача полной обработки видео
    celery_app.py       — конфигурация Celery
    database.py          — подключение к БД
    config.py             — все настройки (из .env)
  pipeline/
    transcribe.py    — обёртка над faster-whisper
    find_moments.py   — обёртка над Claude API + сборка субтитров под момент
  storage/
    uploads/           — загруженные видео
    outputs/            — transcript.json и (позже) готовые нарезки
```

## Запуск (локально)

Нужно 4 процесса одновременно: Redis, Celery worker, Celery Beat, FastAPI.

```bash
# 1. Зависимости
pip install -r requirements.txt

# 2. Redis (брокер задач). Если нет — через docker:
docker run -d -p 6379:6379 redis:7

# 3. Переменные окружения
cp .env.example .env
# впиши свой ANTHROPIC_API_KEY в .env

# 4. Celery worker (отдельный терминал) — здесь реально крутится
#    whisper, вызовы Claude API, ffmpeg-рендер, публикация
celery -A app.celery_app worker --loglevel=info

# 5. Celery Beat (отдельный терминал) — только если нужна отложенная
#    публикация по расписанию; без него всё остальное работает и так
celery -A app.celery_app beat --loglevel=info

# 6. FastAPI сервер (отдельный терминал)
uvicorn app.main:app --reload --port 8000
```

API будет на `http://localhost:8000`, документация (Swagger) — на
`http://localhost:8000/docs`.

## Основной сценарий использования

0. `POST /auth/register` — регистрация (`email` + `password`, минимум 8 символов).
   `POST /auth/login` — вход, получаешь `{access_token, refresh_token}`.
   Дальше все запросы идут с заголовком `Authorization: Bearer <access_token>`.
   Когда access-токен истечёт (час по умолчанию) — `POST /auth/refresh
   {refresh_token}` вместо повторного логина.
1. `POST /videos/upload` — заливаешь mp4, получаешь `video.id`, обработка
   стартует в фоне сразу. Видео привязывается к текущему пользователю.
   Загрузка проверяет длительность (макс. 30 мин) и дневную квоту тарифа
   ДО постановки в очередь — см. раздел про тарифы ниже.
2. Фронтенд опрашивает `GET /videos/{id}` (или подключает WebSocket —
   в этой версии не реализовано, можно добавить) — видит смену статуса:
   `uploaded → transcribing → finding_moments → ready`.
3. Когда `status == "ready"` — `GET /videos/{id}/moments` отдаёт список
   найденных фрагментов с предзаполненными субтитрами.
4. Пользователь правит субтитры (`PATCH /subtitles/{id}`), таймкоды и
   баннер момента (`PATCH /moments/{id}`), выставляет `status: "approved"`.
5. `POST /moments/{id}/render` — рендерит момент через ffmpeg (вырезка,
   вшитые субтитры, наложение баннера, кроп/масштаб под вертикальный
   9:16). По завершении статус момента становится `rendered`,
   `output_path` указывает на готовый файл.
6. `POST /moments/{id}/publish` с `social_account_ids` — публикует
   готовый рендер на одну или несколько подключённых платформ сразу.

Полный цикл от загрузки исходника до опубликованного шортса закрыт
целиком — весь пайплайн реализован и протестирован (см. `tests/`).

## Авторизация

- Пароли хешируются через `bcrypt` напрямую (не `passlib` — у него баг
  совместимости с новыми версиями bcrypt, из-за которого хеширование
  падает с ошибкой про 72 байта).
- Access-токен — JWT, время жизни настраивается через
  `ACCESS_TOKEN_EXPIRE_MINUTES` в `.env` (по умолчанию 60 минут).
- **Обязательно смени `SECRET_KEY`** перед деплоем:
  ```bash
  python3 -c "import secrets; print(secrets.token_hex(32))"
  ```
  Дефолтное значение в `.env.example` годится только для локальной разработки.
- Каждый эндпоинт с видео/моментами/субтитрами проверяет, что объект
  принадлежит текущему пользователю — чужие данные недоступны (в ответ 404,
  чтобы не палить факт существования чужого видео).
- **Refresh-токены реализованы.** `POST /auth/login` возвращает
  `{access_token, refresh_token}`. Когда access-токен истекает (обычно
  через час), фронтенд вызывает `POST /auth/refresh {refresh_token}` и
  получает новый access-токен — без повторного логина. Refresh-токен живёт
  `REFRESH_TOKEN_EXPIRE_DAYS` (по умолчанию 30 дней), хранится в БД только
  как SHA-256 хеш (как пароль — сырой токен из базы не восстановить).
  `POST /auth/logout {refresh_token}` отзывает его явно (например, при
  выходе с "чужого" устройства).

### Смена и восстановление пароля

- `POST /auth/change-password {current_password, new_password}` —
  для залогиненного пользователя, требует текущий пароль. Отзывает ВСЕ
  refresh-токены после смены (если пароль был скомпрометирован, это
  обрывает чужие долгие сессии) — текущий access-токен доработает до
  естественного истечения.
- `POST /auth/forgot-password {email}` — всегда возвращает одинаковый
  ответ независимо от того, существует ли аккаунт (защита от user
  enumeration). Создаёт одноразовый токен восстановления (живёт час,
  настраивается через `PASSWORD_RESET_TOKEN_EXPIRE_MINUTES`), защищён
  rate limit'ом (`FORGOT_PASSWORD_RATE_LIMIT`, по умолчанию 3/минуту).
- `POST /auth/reset-password {token, new_password}` — завершает
  восстановление, тоже отзывает все refresh-токены.

**Email пока не подключён — только dev-заглушка.** `app/email.py`
печатает письмо в лог процесса вместо реальной отправки. Это осознанно
и жёстко заблокировано в проде: `assert_production_safe()` не даст
приложению стартовать с `ENVIRONMENT=production`, пока в `app/email.py`
не появится реальный провайдер (SendGrid/Postmark/Amazon SES/СМТП —
любой). Для локальной разработки и тестов `POST /auth/forgot-password`
дополнительно возвращает сам токен в поле `dev_reset_token` — им можно
сразу пользоваться, не читая лог и не настраивая почту.

### Блокировка аккаунта после неудачных попыток входа

Отдельно от `LOGIN_RATE_LIMIT` (защита по IP, 5 попыток/минуту с одного
адреса) — блокировка **по конкретному аккаунту**, независимо от того, с
какого IP приходят попытки. Защищает от медленного распределённого
перебора пароля одного человека с разных адресов, который IP-based
rate limit не ловит (5 попыток в минуту с 100 разных IP суммарно дают
500 попыток в минуту на один аккаунт).

- `MAX_FAILED_LOGIN_ATTEMPTS` (по умолчанию 5) — после стольки неверных
  паролей подряд аккаунт блокируется на `ACCOUNT_LOCKOUT_MINUTES`
  (по умолчанию 15 минут) — `423 Locked`.
- Блокировка проверяется **до** сверки пароля — даже правильный пароль
  не пустит, пока действует блокировка (проверено тестом отдельно).
- Успешный вход сбрасывает счётчик неудачных попыток.
- Блокировка снимается сама по истечении срока — не нужно ничего чистить
  руками, следующая попытка входа (успешная или нет) видит, что срок
  истёк, и сбрасывает состояние.
- Считается по каждому аккаунту отдельно — блокировка одного не влияет
  на способность других пользователей логиниться.

## Публикация на несколько платформ

Поддерживаются YouTube, TikTok, Instagram (Reels) через единый интерфейс
`app/publishers/base.py::Publisher`. Каждая платформа — отдельный класс
(`YouTubePublisher`, `TikTokPublisher`, `InstagramPublisher`), фабрика
`app/publishers/get_publisher()` выбирает нужный по `SocialAccount.platform`.

### Какие платформы реально включены сейчас

`GET /platforms` возвращает флаг `enabled` для каждой платформы
(`app/config.py::PLATFORM_ENABLED`). Сейчас включён только **YouTube** —
`GET /social-accounts/{platform}/connect` для выключенных платформ отвечает
`503`, а не тихо генерирует ссылку, которая всё равно не будет нормально
работать. Причина в разделе ниже. Когда пройдёшь ревью TikTok и настроишь
Business-аккаунт Instagram — включаются одной переменной окружения:
```
PLATFORM_TIKTOK_ENABLED=true
PLATFORM_INSTAGRAM_ENABLED=true
```

### Прежде чем подключать реальные платформы — важные ограничения

- **YouTube** — открытый API, ключи получаешь сам в Google Cloud Console.
  Дефолтная квота проекта — 10 000 unit/день, загрузка ролика стоит 1600
  unit (~6 загрузок/день на весь проект, не на пользователя).
- **TikTok** — пока приложение не прошло ревью (audit) у TikTok, публикация
  возможна только в приватном режиме (`SELF_ONLY`, видно только автору).
  Публичная публикация от имени пользователей — только после одобрения
  заявки на аудит (может занять недели).
- **Instagram** — работает только с Business/Creator-аккаунтом, привязанным
  к Facebook-странице. Обычный личный Instagram через API не публикует.
  Плюс видео должно быть доступно по публичному URL — просто путь на
  локальном диске сервера не подходит, нужно хранилище вроде S3
  (`PUBLIC_STORAGE_BASE_URL` в `.env`).

### Схема подключения аккаунта (OAuth)

```
GET  /social-accounts/{platform}/connect    → {"authorize_url": "..."}
     фронтенд редиректит пользователя на authorize_url
     (пользователь логинится и подтверждает доступ на стороне платформы)
GET  /social-accounts/{platform}/callback   ← платформа сама сюда редиректит
     сохраняет SocialAccount, редиректит браузер обратно в приложение
GET  /social-accounts                        → список подключённых аккаунтов
DELETE /social-accounts/{id}                  → отключить аккаунт
```

`state`-параметр — подписанный JWT с user_id, живёт 10 минут, защищает
от CSRF без отдельной таблицы временных сессий (`app/oauth.py`).

### Публикация момента

```
POST /moments/{id}/publish
  {
    "social_account_ids": ["<id аккаунта YouTube>", "<id аккаунта TikTok>"],
    "title": "...", "description": "...",
    "scheduled_at": null    // null = опубликовать сразу, иначе — дата/время
  }
```

Создаёт по одному `PublishTarget` на каждый выбранный аккаунт (`status:
queued`). Если `scheduled_at` не задан — сразу ставит Celery-задачу
`publish_target` в очередь. Момент должен быть уже отрендерен
(`moment.output_path` заполнен — это делает задача рендера, следующий шаг
разработки после публикации).

```
GET /moments/{id}/publish-targets   → статус публикации по каждой платформе
```

Статусы `PublishTarget`: `queued → publishing → published` (или `failed`
с `error_message`). При ошибке публикации Celery-задача автоматически
повторяет попытку до 3 раз — полезно, если токен истёк или платформа
временно недоступна.

### Отложенная публикация по расписанию

Реализовано через Celery Beat. `POST /moments/{id}/publish` с `scheduled_at`
в будущем создаёт `PublishTarget` со `status=queued`, но НЕ отправляет
задачу немедленно. Раз в минуту `dispatch_scheduled_publishes`
(`app/tasks.py`, расписание в `app/celery_app.py::beat_schedule`) находит
все таргеты, чьё время публикации уже наступило, и ставит их в очередь.

Защита от повторной отправки: диспетчер меняет статус на `publishing`
**одним bulk-update в той же транзакции**, что и выборка — до вызова
`.delay()`. Если бы статус менялся только когда воркер реально начнёт
обработку, при заполненной очереди следующий тик Beat (через минуту) мог
бы увидеть тот же таргет всё ещё в `queued` и отправить его повторно —
это протестировано отдельно (`test_dispatch_scheduled_publishes_does_not_double_dispatch`).

Требует отдельный процесс на проде и локально:
```bash
celery -A app.celery_app beat --loglevel=info
```
(в дополнение к `celery -A app.celery_app worker`, который уже нужен был
для остальных фоновых задач).

### Безопасность токенов

`SocialAccount.access_token`/`refresh_token` шифруются перед записью в БД
(`app/token_crypto.py`, Fernet). Ключ — `TOKEN_ENCRYPTION_KEY` в `.env`,
**отдельный** от `SECRET_KEY` (JWT), чтобы утечка одного не компрометировала
другое. Остальной код (publishers/*.py, oauth.py) работает с
`account.access_token` как с обычной строкой — шифрование/дешифрование
прозрачно через python-property на модели `SocialAccount`.

Сгенерировать постоянный ключ:
```bash
python3 -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```
Если `TOKEN_ENCRYPTION_KEY` не задан при `ENVIRONMENT=development` — ключ
генерируется автоматически на время запуска процесса (только для удобства
разработки, все токены станут нерасшифровываемыми после рестарта). При
`ENVIRONMENT=production` без заданного ключа приложение откажется
стартовать (`assert_production_safe()`).

**Что НЕ шифруется и стоит иметь в виду**: пароли пользователей (уже
хешированы bcrypt — это правильно, хешировать не то же самое, что шифровать,
и для паролей так и должно быть), refresh-токены самого приложения (тоже
хешированы, не шифрованы — тот же принцип). Шифрование именно для
access/refresh-токенов соцаккаунтов — потому что их (в отличие от пароля)
иногда нужно расшифровать обратно для реального использования (вызова API
платформы).

## Тарифы, дневные квоты и монеты

Логика целиком в `app/billing.py`, конфигурация лимитов и цен — в
`app/config.py`. Правки лимитов/цен — это просто изменение чисел там,
код менять не нужно.

### Требование: ffmpeg должен быть установлен в системе

Определение длительности видео идёт через `ffprobe` (часть ffmpeg),
вызывается напрямую как системная команда, а не через pip-пакет:
```bash
sudo apt install ffmpeg   # если ещё не стоит
```

### Правила (текущие значения в `app/config.py`)

| Тариф | Нарезок в день бесплатно | Аккаунтов на каждую платформу |
|-------|---------------------------|-------------------------------|
| free  | 1                          | 1                              |
| tier2 | 5                          | 3                              |
| tier3 | 9                          | 5                              |

- Максимальная длина одного видео на вход — **30 минут**, одинаково для
  всех тарифов (`MAX_VIDEO_DURATION_SECONDS`). Проверяется через ffprobe
  сразу при загрузке, до постановки в очередь на транскрипцию — если
  видео длиннее, оно отклоняется с понятной ошибкой и не тратит ничьё
  время на бесполезную обработку.
- "Аккаунтов на каждую платформу" — лимит применяется отдельно к каждой
  платформе. То есть на tier2 можно подключить 3 YouTube + 3 TikTok +
  3 Instagram (9 аккаунтов всего), а не 3 суммарно.
- Превышение дневной квоты нарезок → списывается `EXTRA_CUT_COST_COINS`
  монет за конкретную нарезку (разовая оплата, квота на завтра не меняется).
- Превышение лимита аккаунтов на платформу → списывается
  `EXTRA_ACCOUNT_SLOT_COST_COINS` монет, и лимит увеличивается **навсегда**
  (это покупка постоянного дополнительного слота, а не разовая оплата).
- Если монет не хватает — `402 Payment Required` с понятным сообщением,
  ничего не списывается и не создаётся.

### Начисление монет и смена тарифа — ТОЛЬКО через оплату

`POST /billing/coins/webhook` и `POST /billing/subscription/webhook` —
это то, что должен дёргать твой платёжный провайдер (для российского рынка
это обычно ЮKassa или CloudPayments; Stripe/PayPal для РФ сейчас не
работают) после подтверждённой оплаты. Они защищены общим секретом
(`PAYMENT_WEBHOOK_SECRET`) — **это временная заглушка**, перед продакшеном
нужно заменить на настоящую проверку HMAC-подписи конкретно того
провайдера, которого подключишь (у каждого свой механизм подписи вебхуков,
нужно смотреть его документацию).

Сам процесс оплаты (форма оплаты, редирект на страницу провайдера,
обработка успеха/отказа) в этот бэкенд не входит — это отдельная
интеграция с SDK/API конкретного провайдера, обсудим отдельно, когда
определишься, через кого принимать платежи.

Для локальной разработки без реальной оплаты есть dev-only эндпоинты
(отключены при `ENVIRONMENT=production`):
```
POST /billing/dev/grant-coins   { "amount": 500 }
POST /billing/dev/set-tier      { "tier": "tier2" }
```

## Рендер (ffmpeg)

`pipeline/render.py` — вырезка сегмента из исходника, кроп/масштаб под
вертикальный 9:16, вшитые субтитры, наложение баннера, всё одним проходом
ffmpeg. Запускается фоновой Celery-задачей `render_moment_task` через
`POST /moments/{id}/render` (момент должен быть в статусе `approved`).

Известный нюанс, на который наткнулись при тестировании: ffmpeg/libass
падает с ошибкой `Unable to open ...srt`, если файл субтитров пустой (нет
реплик) — это баг самого libass, не путей/прав доступа. Поэтому фильтр
субтитров подключается только если у момента реально есть хотя бы одна
реплика — для моментов без субтитров рендер идёт без них.

## Мультиаккаунтинг (обход free-лимита новыми email)

`same_ip_free_signups_last_7d` в ответе `GET /billing/me` — счётчик
free-регистраций с того же IP за последние 7 дней. Это **информационный
сигнал, не блокировка**: IP — ненадёжный признак (общежития, офисы,
мобильные сети с CGNAT легитимно шарят один внешний IP на десятки людей),
автоматический бан по нему бил бы по настоящим пользователям чаще, чем по
злоупотребляющим. Если проблема реально проявится на практике — следующий
шаг это подтверждение по SMS при регистрации (Twilio/SMS.ru или похожий
провайдер), это отдельная интеграция, не то, что стоит делать превентивно.

## Живой предпросмотр видео (отдача медиафайлов)

`GET /videos/{id}/file` и `GET /moments/{id}/banner/file` отдают исходный
видеофайл и картинку баннера напрямую — нужно для настоящего `<video>` в
редакторе на фронтенде (раньше там была статичная заглушка).

**Авторизация через query-параметр `?token=`, не через заголовок.** Тег
`<video>` в браузере не может слать кастомные заголовки на свои
собственные запросы (включая Range-запросы при перемотке), поэтому это
единственный практичный способ авторизовать такой запрос. Используется
ТОЛЬКО для этих двух эндпоинтов (`app/auth.py::get_media_user`) — обычные
JSON API по-прежнему требуют заголовок `Authorization`, чтобы токен не
оседал в логах/истории браузера без необходимости.

**Честное ограничение по форматам**: браузер нативно проигрывает только
`mp4`/`webm`. Если пользователь загрузит `.mkv`/`.avi` — сам файл
отдастся корректно и **рендер всё равно отработает** (ffmpeg не
привередлив к формату входа), но живой предпросмотр в редакторе для
такого файла не запустится — это ограничение самого браузера, не бэкенда.

**Отдельное техническое примечание для тех, кто будет тестировать это в
headless-браузере** (Playwright/Puppeteer/CI): открытая сборка Chromium,
которую они используют по умолчанию, часто собрана **без поддержки
H.264** (лицензионное ограничение проприетарного кодека) — видео с
H.264 в таком окружении не воспроизведётся (`MEDIA_ERR_SRC_NOT_SUPPORTED`),
хотя в реальном Chrome/Firefox/Edge пользователя всё будет работать
нормально. Для тестов в headless-окружении используйте VP9/WebM
(`ffmpeg -c:v libvpx-vp9 ...`) — этот кодек открытый и всегда
поддерживается.



Опциональный шаг перед публикацией: рандомизированный набор лёгких
трансформаций (зеркалирование, кроп/зум 1.5-5%, скорость ±3-5%,
цветокоррекция, лёгкий шум, сдвиг тона звука, зачистка метаданных), чтобы
разные подключённые аккаунты не публиковали побитово идентичный файл.

**Что это реально даёт и чего не даёт** — важно понимать это трезво, а не
как гарантию:
- Снижает точное совпадение по хэшу контента между копиями одного рендера.
- **Не отменяет** того, что публикация похожего контента с нескольких
  аккаунтов одного человека нарушает пользовательские соглашения YouTube/
  TikTok/Instagram (политики про спам и множественные аккаунты) — они
  ловят такое и по другим сигналам (паттерны публикации, поведение),
  не только по хэшу файла. Это инструмент снижения технического
  дублирования, а не защита от бана как такового.

### Как включить

```
POST /moments/{id}/publish
  {
    "social_account_ids": [...],
    "uniqueize": true
  }
```

Каждый `PublishTarget` с `uniqueize=true` получает СВОЙ случайный набор
параметров (новый при каждом вызове, без фиксированного seed) — то есть
если один момент публикуется на 5 аккаунтов TikTok сразу, все 5 копий
визуально и по хэшу разные между собой, не только отличаются от исходника.
Временный файл создаётся непосредственно перед загрузкой и удаляется сразу
после (успешной или неудачной) попытки публикации — не занимает место
на диске сверх времени самой публикации.

### Дневная квота по тарифам

Уникализация не безлимитна на бесплатном тарифе — так же, как нарезки
и слоты аккаунтов, она ограничена в день, конфигурация в
`app/config.py::DAILY_UNIQUEIZE_LIMITS`:

| Тариф | Уникализаций в день бесплатно |
|-------|-------------------------------|
| free  | 2                              |
| tier2 | 5                              |
| tier3 | 10                             |

**Считается ЗА НАРЕЗКУ, не за аккаунт.** Один вызов `POST
/moments/{id}/publish {"uniqueize": true}` — это одно списание квоты,
даже если этот вызов создаёт `PublishTarget` сразу на 5 подключённых
аккаунтов (у каждого будет своя уникализированная копия, но потрачена
только 1 единица дневного лимита). Публикация без `uniqueize` квоту не
трогает вообще — можно публиковать сколько угодно раз в рамках лимита
нарезок/аккаунтов, просто без уникализации.

Отслеживается отдельной таблицей `UniqueizeUsage` (не через
`PublishTarget`, потому что один вызов может создать несколько таргетов
сразу — квоту считаем по вызовам, а не по строкам).

**Цена монет за превышение лимита пока не определена** — сейчас
превышение просто блокируется (`402`), ничего не списывается. Когда
цена будет решена, добавляется в `ensure_uniqueize_allowed()`
(`app/billing.py`) по тому же паттерну, что уже используется для нарезок
и слотов аккаунтов (`spend_coins(...)`) — минутное изменение поверх уже
готовой квоты.

`GET /billing/me` отдаёт `uniqueize_used_today`/`uniqueize_daily_limit`
вместе с остальными показателями тарифа.

## Два режима работы: облачный (celery) и локальный (local)

`RUNNER_MODE` в `.env` переключает, как выполняются фоновые задачи
(транскрипция, рендер, публикация):

- **`celery`** (по умолчанию) — то, что описано в разделе "Запуск
  (локально)" выше: Redis + Celery worker + Celery Beat как отдельные
  процессы. Нужен для облачного SaaS с несколькими пользователями —
  масштабируется на несколько машин-воркеров.
- **`local`** — для desktop-версии (см. план ниже). Задачи выполняются в
  пуле потоков внутри того же процесса FastAPI — Redis, Celery, Docker
  не нужны вообще. Отложенная публикация по расписанию тоже работает
  (`app/local_scheduler.py` — фоновый поток вместо Celery Beat, проверяет
  раз в минуту).

Бизнес-логика задач (`app/tasks.py`) написана один раз и используется в
обоих режимах — каждая задача разбита на `_core`-функцию (чистая логика)
и тонкую Celery-обёртку; `_core`-функция дополнительно регистрируется как
локальная реализация через `app/job_runner.py::register_local()`. Весь
остальной код (`app/main.py`) вызывает только `dispatch(task, *args)` и
не знает, какой режим активен.

Протестировано в `tests/test_local_mode.py` — реальный рендер через
ffmpeg и реальная публикация (с замоканным внешним API) в локальном
потоке, без единого обращения к Celery/Redis.

**Ограничение локального режима**: ретраи (self.retry в Celery) заменены
на простой синхронный retry с `time.sleep()` внутри фонового потока
(`app/tasks.py::_retry_sync`) — для одного пользователя на своём
компьютере этого достаточно, устойчивость к падению всего процесса
(как в Celery с персистентной очередью в Redis) здесь не гарантируется —
если закрыть приложение посреди задачи, она просто не завершится, и
её нужно будет запустить заново.

## План: desktop-приложение для Windows

Цель — `.msi`-инсталлятор, после которого пользователь получает
полноценное окно приложения, без Python/ffmpeg/Docker на виду.

1. ✅ **Убрать зависимость от Redis/Celery** — сделано, см. раздел выше
   (`RUNNER_MODE=local`).
2. Собрать backend в один `.exe` через **PyInstaller** — конечный
   пользователь не ставит Python вообще.
3. Построить **фронтенд** (React) — минимальный рабочий цикл: логин →
   загрузка → редактор моментов → публикация.
4. Обернуть всё в **Tauri**, настроить сборку `.msi` для Windows.
   ffmpeg.exe/ffprobe.exe кладутся в ресурсы инсталлятора напрямую —
   без системной установки.
5. Whisper-модель **скачивается при первом запуске** (не вшита в
   инсталлятор) — решение принято осознанно ради компактного инсталлятора.
6. Протестировать на чистой Windows-машине без Python/ffmpeg/Docker —
   финальная проверка самодостаточности инсталлятора.

Шаги 2-4 — хороший кандидат на делегирование Claude Code: там есть
реальный доступ к файловой системе и возможность ставить Node/Rust
тулчейны и по-настоящему собирать `.exe`/`.msi`, чего не сделать в этой
песочнице (нет Windows и нужных тулчейнов).

## Миграции базы данных (Alembic)

Схема БД версионируется через Alembic (`alembic/versions/`) — вместо
`Base.metadata.create_all()`, который умеет только создавать отсутствующие
таблицы и не умеет обновлять уже существующие (добавить колонку, изменить
тип). Без миграций первое же изменение модели после запуска в прод либо
уронило бы приложение на живой базе, либо потребовало бы ручных ALTER
TABLE на базе с реальными пользователями.

### Два режима — два способа применения миграций

- **`RUNNER_MODE=local` (desktop)** — миграции гоняются **автоматически**
  при каждом старте приложения (`_run_migrations_to_head()` в `main.py`).
  Пользователю desktop-версии не нужно ничего вводить руками — база сама
  доводится до актуальной схемы. `alembic upgrade head` идемпотентен:
  на уже актуальной базе просто ничего не делает, так что гонять его на
  каждом старте безопасно.
- **`RUNNER_MODE=celery` (облачный SaaS)** — миграции **НЕ** гоняются
  автоматически при старте приложения. Это осознанно: если поднимается
  несколько инстансов сервера одновременно (что нормально для прода),
  каждый из них пытался бы мигрировать базу параллельно — гонка условий.
  Здесь миграция — явный шаг деплоя, выполняемый один раз перед
  перезапуском серверов:
  ```bash
  alembic upgrade head
  ```

### Как добавлять новые миграции

После любого изменения в `app/models.py`:
```bash
alembic revision --autogenerate -m "краткое описание изменения"
```
Alembic сравнит текущие модели с реальной схемой БД и сам сгенерирует
файл миграции в `alembic/versions/`. **Всегда открой и проверь
сгенерированный файл** — автогенерация не видит переименований (увидит
их как "удалить старую колонку + создать новую", что теряет данные) и не
ловит некоторые изменения ограничений. Переименование колонки нужно
дописывать руками через `op.alter_column(..., new_column_name=...)`.

Протестировано вручную: реальный пользователь в базе пережил добавление
новой колонки через `alembic upgrade head` без потери своих данных
(значение новой колонки стало `NULL` для существующей строки, сама
строка и её `id` остались нетронуты).

### batch-режим для SQLite

`alembic/env.py` включает `render_as_batch=True` — SQLite не умеет
многие `ALTER TABLE` напрямую (например, менять тип колонки), batch-режим
эмулирует их через "создать новую таблицу → скопировать данные → удалить
старую". На Postgres (прод) это не нужно, но и не мешает — включено
всегда для единообразия между dev (SQLite) и продом (Postgres).

## На проде

- SQLite → Postgres (`DATABASE_URL=postgresql://...`), схема не меняется.
- **`alembic upgrade head` перед перезапуском серверов** — обязательный
  шаг деплоя при `RUNNER_MODE=celery` (см. раздел про миграции выше),
  автоматически не запускается.
- Redis и Celery worker — как отдельные сервисы/контейнеры.
- Файлы (`storage/`) лучше вынести на S3-совместимое хранилище, если
  видео много — на диске одной машины это не масштабируется.
- `whisper` на GPU-инстансе — на CPU обработка часового эпизода может
  занимать 15-30+ минут, на GPU — пара минут.
- `ffmpeg`/`ffprobe` должны быть установлены в системе (не pip-пакеты) —
  и на API-сервере (для проверки длительности при загрузке), и на
  Celery worker (для рендера).
- Обязательно задать `SECRET_KEY`, `TOKEN_ENCRYPTION_KEY`,
  `PAYMENT_WEBHOOK_SECRET` — при `ENVIRONMENT=production` приложение
  откажется стартовать, если что-то из этого не задано или осталось
  дефолтным (`assert_production_safe()` в `app/config.py`).
- Прогонять `pytest` в CI перед каждым деплоем — набор тестов уже находил
  реальные баги (пустой SRT ломает ffmpeg, JWT-коллизия при одинаковой
  секунде создания) на этапе разработки, а не в проде на живых пользователях.
